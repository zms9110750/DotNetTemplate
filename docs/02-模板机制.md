# 02 · 模板机制

这一篇解释「`dotnet new` 到底对哪些文件做了什么」，以及 `zmsTemplate/.template.config/template.json` 里每一项的用意。

## 两种条件语法（最容易搞混的一点）

这个仓库里同时存在 **两套完全不同的条件机制**，处理者不同、时机不同：

| 语法 | 长什么样 | 谁处理 | 何时 | 用在哪 |
|---|---|---|---|---|
| **模板条件** | `{{TIsLib}}`、`//#if (TIsLib)`、`<!--#if (TIsLib) -->` | `dotnet new` 模板引擎 | 生成项目的那一刻 | `template.json`、`MyApp.slnx`、`README.md`、`SampleTests.cs` |
| **编译条件** | `#if USE_LOG`、`#if IS_CLI` | C# 编译器（Roslyn） | 每次编译 | `Global.cs`、`Program.cs` |

**为什么必须分开**：模板条件决定"文件里有没有这段代码"，编译条件决定"这段代码要不要编进程序集"。
混用就会出现"属性开关开了但代码已经被模板删掉"这类难以调试的问题。

**实测结论**：

- `{{TIsLib}}` 被替换为 `True` / `False`（**.NET 布尔格式，首字母大写**），而 `Directory.Build.props`
  里写成 `'$(IsLib)' == 'true'` —— 靠 **MSBuild 字符串比较大小写不敏感**才能成立。
  改属性名或比较值时不要想当然地认为大小写必须一致。
- `MyApp.slnx` 里的 `<!--#if (TIsLib) -->` **确实生效**：以
  `--TIsLib true --TIsCli true --TIsTest true` 生成后，`Foo.slnx` 里只剩
  `/src/Foo/`、`/samples/Foo.Cli/`、`/test/Foo.Test/` 三项，注释与未选项都不残留。

## template.json 逐项

```jsonc
{
  "identity": "OpenSourceProjectTemplate",  // 模板唯一标识（升级/冲突判断靠它）
  "shortName": "zms",                       // 命令行 `dotnet new zms`
  "sourceName": "MyApp",                    // 生成时把内容与文件名里的 MyApp 换成 -n 的名字
  "preferNameDirectory": true,              // `-n Foo` 默认输出到 Foo/ 目录
  "classifications": ["Console", "Library", "Test"]
}
```

### symbols

| 符号 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `TIsLib` | bool | false | 生成类库到 `src/` |
| `TIsCli` | bool | false | 生成 CLI 项目 |
| `TIsGui` | bool | false | 生成 GUI 项目 |
| `TIsTest` | bool | false | 生成测试项目到 `test/` |
| `TWithSamples` | bool | **true** | 是否带示例代码（CLI 命令树 / GUI 计数器）；false 时生成空壳 |
| `TUsePolly` | bool | false | 引入 Polly 弹性/重试 |
| `TUseFusionCache` | bool | false | 引入 FusionCache 缓存 |
| `TUseDI` | bool | false | 引入 DI 容器 |
| `TUseLog` | bool | false | 引入 Serilog 日志 |
| `AuthorName` | text | "" | 作者名，写进 `Directory.Build.props` 并影响命名空间根 |

**为什么 `TWithSamples` 默认 true、其余默认 false**：新项目最需要的是"能看能跑的参照物"，所以示例默认给；
而 Polly / 缓存 / 日志属于"用到才要"，默认关闭，避免凭空多出十几个包引用。

**为什么开关统一带 `T` 前缀**：把这些"模板参数"与 `Directory.Build.props` 里的 MSBuild 属性
（`IsLib` / `UseLog` 等，不带 `T`）区分开。`{{TIsLib}}` 只做一次替换、落成 `<IsLib>`，之后一切判断都用 `<IsLib>`。

### sources.modifiers —— 裁剪规则（核心）

```jsonc
{
  "copyOnly": ["**/Global.cs"],
  "modifiers": [
    { "condition": "true",                            "exclude": ["src/**/*","samples/**/*","test/**/*"] },
    { "condition": "(TIsLib == true)",                "include": ["src/MyApp/**/*"] },
    { "condition": "(TIsLib == true && TIsCli == true)",  "include": ["samples/MyApp.Cli/**/*"] },
    { "condition": "(TIsLib == true && TIsGui == true)",  "include": ["samples/MyApp.GUI/**/*"] },
    { "condition": "(TIsLib == false && TIsCli == true)", "include": ["src/MyApp.Cli/**/*"] },
    { "condition": "(TIsLib == false && TIsGui == true)", "include": ["src/MyApp.GUI/**/*"] },
    { "condition": "(TIsTest == true)",               "include": ["test/**/*"] }
    // 其余见文件全文（示例开关、EmptyApp 与 App.razor 的互补排除）
  ]
}
```

**为什么第一条是"默认全排除"**：`src/` `samples/` `test/` 下的东西**没有一个是无条件生成的**，
先整体排除、再按条件 include，可以避免"新增了文件但忘了排除"导致它在不该出现的组合里生成出来。
**新增文件时，请检查是否需要给某条 modifier 补 include。**

**为什么 `src/` 与 `samples/` 各有一套同名项目**：布局取决于 `TIsLib`（见 [01](01-语义与设计意图.md) 目标 2）——
`MyApp.Cli` 在"有 lib"时进 `samples/`、在"无 lib"时进 `src/`。两套文件**内容几乎完全相同**
（实测哈希一致：`Program.cs`、`Tree/**`、`Options/Janken.cs`、`App.razor`、`wwwroot/index.html` 等），
差异只在 `csproj`（描述文字、是否 `ProjectReference` 到 lib）与 `appsettings.json`。

> ⚠️ 这是一个**已知的维护代价**：改 CLI/GUI 示例逻辑时，`src/` 与 `samples/` 两份都要改。
> 这是"布局切换"换来的代价，当前是有意接受的。

**示例开关的两条互补排除**：`TWithSamples == false` 时排除 CLI 的 `Tree/` `Options/` `Shared/`；
GUI 侧则用 `EmptyApp.razor` 替换 `App.razor`（计数器），靠一对互补的 exclude 实现。

### copyOnly

```jsonc
"copyOnly": ["**/Global.cs"]
```

**含义**：这个文件**只复制、不做模板符号替换**。

**为什么**：`Global.cs` 里全是 C# 预处理指令（`#if USE_POLLY` / `#if IS_CLI`），
必须在**编译期**由 Roslyn 处理，而不是在生成期被模板引擎动过。

### specialCustomOperations

```jsonc
"**/*.md": { "operations": [ conditional, if: ["//#if"], else: ["//#else"], elseif: ["//#elseif"], endif: ["//#endif"], wholeLine: true, trim: true ] }
```

**为什么只给 `.md` 配**：Markdown 本身没有注释语法，所以为它单独约定 `//#if` 这种"伪注释"来写条件段落
（`zmsTemplate/README.md` 里大量使用）。这是**为 Markdown 约定的语法**，不要照搬到别的文件类型。

### postActions

```jsonc
{ "actionId": "B175A520-76F8-46F5-800C-2B55B8A0E65F", "args": { "noRestore": "false" }, "continueOnError": true }
```

**含义**：生成后自动执行 `dotnet restore`。

**实测注意**：这个 action **只在以 nupkg 安装模板时可用**。用
`dotnet new install <本地路径>` 安装会报 `不支持发布操作 b175a520-...`（不中断生成，但 restore 不会自动执行），
本地验证模板时要自己补一次 `dotnet restore`。

## 打包

`DotNetTemplate.nuspec`：

```xml
<packageTypes><packageType name="Template" /></packageTypes>
<files>
  <file src="zmsTemplate/**/*" target="content/zmsTemplate/" exclude="zmsTemplate/**/bin/**;zmsTemplate/**/obj/**" />
</files>
```

**为什么用 nuspec 而不是 SDK 的 `<PackageId>` 打包**：模板包的内容是**文件树**（不是编译产物），
nuspec 的 `<files>` 直接表达"把整个 `zmsTemplate/` 原样搬进去"。

**为什么 exclude bin/obj**：模板源目录被构建过之后会留下 `bin/` `obj/`，不排除就会一起打进包里。

**`build/FormatOnce.proj` 会自动进包**：`zmsTemplate/**/*` 是通配，且 modifiers 只排 `src/` `samples/` `test/`，
所以新增这个文件不需要改任何打包配置（已确认）。

**版本号是个坑**：`dotnet pack -p:Version=X` **不会**覆盖 nuspec 里的 `<version>` 元素，
所以两套 CI 都是**先用 PowerShell 正则替换 nuspec 的 `<version>` 再打包**（见 [05](05-GitHub工作流.md)）。

## 本地验证模板的正确姿势

```powershell
dotnet new install <仓库>\zmsTemplate
dotnet new zms -n Foo --TIsLib true --TIsCli true --TIsTest true
# ...检查生成结果...
dotnet new uninstall <仓库>\zmsTemplate      # 记得卸载
```

**注意**：机器上若已装过 `zms9110750.DotNetTemplate`，`dotnet new zms` 会出现
"以下模板使用相同的标识 OpenSourceProjectTemplate" 警告 —— 排查"生成结果不对"时**先 `dotnet new uninstall` 清干净**。
