# 04 · 项目结构与示例

## 布局：为什么 `src/` 和 `samples/` 各有一套同名项目

生成结果取决于 `TIsLib`（见 [01](01-语义与设计意图.md) 目标 2）：

| 配置 | 类库 | CLI / GUI |
|---|---|---|
| `TIsLib=true` | `src/MyApp/` | `samples/MyApp.Cli/`、`samples/MyApp.GUI/` |
| `TIsLib=false` | 无 | `src/MyApp.Cli/`、`src/MyApp.GUI/` |

所以模板里必须**同时存在** `src/MyApp.Cli` 与 `samples/MyApp.Cli`（GUI 同理），
由 `template.json` 的 modifiers 按条件只保留一份。

**实测：两份内容几乎完全相同**（哈希一致）：

```
MyApp.Cli\Program.cs                          一致
MyApp.Cli\Tree\CliRoot.cs                     一致
MyApp.Cli\Tree\Rand\RandCommand.cs            一致
MyApp.Cli\Tree\Rand\Janken\JankenCommand.cs   一致
MyApp.Cli\Tree\Hello\HelloCommand.cs          一致
MyApp.Cli\Options\Janken.cs                   一致
MyApp.GUI\Program.cs                          一致
MyApp.GUI\App.razor                           一致
MyApp.GUI\EmptyApp.razor                      一致
MyApp.GUI\_Imports.razor                      一致
MyApp.GUI\wwwroot\index.html                  一致
MyApp.Cli\appsettings.json                    不同（字段略有差异）
```

差异只集中在 `csproj`（`Description` 文案、是否 `ProjectReference` 到类库）与 `appsettings.json`。

> ⚠️ **维护代价**：改示例逻辑要改两份。这是有意接受的取舍 —— 换来的是"生成的仓库里没有用不到的目录"。

### `csproj` 里的两处条件

```xml
<!-- samples 版：有 lib 才引用 -->
<ItemGroup Condition="'$(IsLib)' == 'true'">
  <ProjectReference Include="..\..\src\MyApp\MyApp.csproj" />
</ItemGroup>
```

`IsLib` 是 MSBuild 属性（`{{TIsLib}}` 替换而来），所以这个条件在**构建期**判断。
生成到 `samples/` 的组合里 `IsLib` 恒为 true，条件看起来"多余"，但它让同一份 csproj 文本可以安全地
放在两种布局下 —— 也是"两份文件只差一点"的原因。

**为什么 `IS_CLI` / `IS_GUI` / `IS_TEST` 写在 csproj 而不是 `Directory.Build.props`**：
它们描述的是"**这个项目**是什么壳"，属于项目自身特征；而 `USE_POLLY` / `USE_LOG` 这类是"**整个仓库**
启用了什么能力"，属于全局开关。放在各自的正确层级，才不会出现"CLI 项目被标成 GUI"这种事。

## CLI 项目（`System.CommandLine`）

### 目录约定

```
Tree/                     ← 镜像命令树层级
├── CliRoot.cs            ← 根命令，注册所有子命令
├── Rand/
│   ├── RandCommand.cs    ← `rand`
│   └── Janken/
│       └── JankenCommand.cs  ← `rand janken`
└── Hello/
    └── HelloCommand.cs   ← `hello`
Options/                  ← 与命令行参数/选项绑定的 enum
Shared/                   ← 被多个同级命令共用的子命令
```

**为什么目录镜像命令树**：看到 `rand janken` 就能直接定位到 `Tree/Rand/Janken/JankenCommand.cs`，
不需要全局搜索命令名。命令树每深一层，文件夹就深一层。

**为什么 `Options/` 只放 enum**：`Option<Janken>` 这类绑定需要一个类型，而这个类型是"命令行概念"，
不属于业务逻辑。**为什么 `Shared/` 专门放复用子命令**：`Shared/README.txt` 举的例子是
"浏览收藏夹 / 浏览热门 / 浏览推荐 都有 `download` 子命令"——把 `DownloadCommand` 放 `Shared/`，
各父命令引用即可，避免三份拷贝。

**为什么用 `.txt` 而不是 `.md` 写这两个说明**：`README.txt` 只是给人看的占位提示，
不出现在任何构建产物里；用 `.txt` 避免被当作 Markdown 渲染目标或文档站抓取。
（`compiler` 不会编译 `.txt`，也不会被 `dotnet format` 处理。）

### 每个命令的形状

```csharp
public static class HelloCommand
{
    public static Argument<string> NameArg { get; } = new("name") { Description = "Your name" };

    public static Command Cmd { get; } = Init(new Command("hello", "输出问候语")
    {
        NameArg,
    });

    private static Command Init(Command cmd)
    {
        cmd.SetAction(Execute);
        return cmd;
    }

    private static void Execute(ParseResult ctx)
    {
        Console.WriteLine($"hello {ctx.GetValue(NameArg)}");
    }
}
```

**为什么要有 `Init` 这一层包装**：C# 的**静态属性初始化器里不能写语句块**，而 `SetAction` 是方法调用。
所以用 `Init(...)` 把"构造命令对象"和"绑定 action"串起来，同时保证 `Cmd` 是只读静态属性
（懒加载一次、全局唯一）。这是整个 CLI 的固定模式，三个命令完全一致。

**为什么 action 单独抽成 `Execute` 方法**：命令定义（选项/参数）与执行体分离，
`Execute` 里就能写正常的多语句代码，也让测试/阅读时能直接跳到逻辑。

### 三个示例命令

| 命令 | 定义 | 关键点 |
|---|---|---|
| （根命令） | `CliRoot.Root` + `Argument<string[]> items` | 无子命令时逐行输出所有参数 |
| `hello <name>` | `Argument<string> NameArg` | 最简单的"必填位置参数"示范 |
| `rand` | `--min`(0) / `--max`(100) / `--count`(1) | `--count` 用 `Validators` 限制不超过 100 |
| `rand janken` | `--hand`(枚举 `Janken`，默认 Rock) | `Option<Janken>` 演示枚举绑定；与电脑猜拳 |

`rand janken` 的胜负判定用的是**枚举下标算术**：`(playerIdx + 1) % 3 == cpuIdx` 表示玩家赢
（`Rock=0, Scissors=1, Paper=2`，此顺序下 +1 取模正好是"克制"关系）。
**改动 `Janken` 枚举成员顺序会破坏这条规则**。

`CliRoot` 的入口在 `Program.cs`：

```csharp
#if (TWithSamples)
return CliRoot.Root.Parse(args).Invoke();
#else
return 0;
#endif
```

注意这是**模板条件**（`TWithSamples`），因为 `TWithSamples=false` 时 `CliRoot.cs` 根本不会被生成。

## GUI 项目（`Photino.Blazor` + `Masa.Blazor`）

### 为什么选这套

`Photino.Blazor` 是 WebView 宿主的 Blazor 桌面应用，**不需要 WPF / WinForms**，
Windows / Linux / macOS 三平台都能跑；`Masa.Blazor` 提供 Material 风格组件。
对一个"开源项目模板"来说，跨平台 + 不绑死 Windows 是必要条件。

`csproj` 用 `Sdk="Microsoft.NET.Sdk.Razor"`（需要 Razor 编译），`OutputType` 是 `WinExe`。

### `CheckPhotinoFramework` target

```xml
<Target Name="CheckPhotinoFramework" BeforeTargets="CoreCompile"
        Condition="'$(TargetFramework)' != 'net8.0' And '$(TargetFramework)' != 'net9.0' And '$(TargetFramework)' != 'net10.0'">
  <Error Text="PhotinoX.Blazor 当前仅支持 net8.0/net9.0/net10.0。当前目标: $(TargetFramework)。请调整 TargetFramework 或更新 PhotinoX.Blazor。" />
</Target>
```

**为什么需要**：`PhotinoX.Blazor` 有明确的 TFM 白名单。如果使用者把 `TargetFramework` 改成
`net11.0`，缺少这个 target 时会得到一堆难以定位的编译/运行错误；有了它，会在编译前直接给出
"改哪里"的中文提示。**这是一个"错误信息友好化"的 target，没有它功能也正常。**

### `Program.cs` 要点

```csharp
var appBuilder = PhotinoBlazorAppBuilder.CreateDefault(args);
appBuilder.Services.AddMasaBlazor();
// USE_FUSIONCACHE / USE_LOG 条件块：调用 GlobalUsing 的装配方法
appBuilder.RootComponents.Add<App>("#app");     // TWithSamples=false 时是 EmptyApp
var app = appBuilder.Build();
app.MainBlazorWindow.Window.SetTitle("MyApp").SetUseOsDefaultSize(false).SetSize(1280, 750);
app.Run();
```

- **为什么 `SetUseOsDefaultSize(false)` + `SetSize(1280, 750)`**：Photino 默认沿用系统窗口尺寸，
  显式设成固定初始尺寸让 GUI 一打开就是可用的布局宽度（Masa 的导航栏在窄窗口下会挤压）。
- **为什么 `[STAThread]`**：Windows 上 WebView 宿主线程模型要求。

### `wwwroot/`

- `index.html`：`<script src="_framework/blazor.webview.js">` 是 Blazor WebView 宿主脚本；
  `<script src="_content/Masa.Blazor/js/masa-blazor.js">` 与对应 css 由 Masa 包提供（`_content/` 路径）；
  图标字体走 CDN（`cdn.masastack.com`），所以**首次运行需要联网**才能看到图标。
- 导航栏右侧的 Masa logo 指向官方文档（`App.razor` 里的 `<MButton Href="https://docs.masastack.com/">`）。

### `App.razor` vs `EmptyApp.razor`

| 文件 | 用于 |
|---|---|
| `App.razor` | `TWithSamples=true`（默认）：一个可点击计数器的示例页面 |
| `EmptyApp.razor` | `TWithSamples=false`：同样外壳，去掉计数器 |

两者共享同一套 `MApp` / `MAppBar` / `MMain` 结构，差异只在中间的内容块 —— 这样"关掉示例"时
界面骨架仍然完整。`template.json` 用一对互补的 exclude 在两者之间切换。

## 测试项目（xUnit v3）

```xml
<OutputType>Exe</OutputType>
<PackageReference Include="Microsoft.NET.Test.Sdk" Version="18.8.1" />
<PackageReference Include="xunit.v3" Version="3.2.2" />
<PackageReference Include="xunit.runner.visualstudio" Version="3.1.5" />
```

**为什么 `OutputType` 是 `Exe`（而不是 `Library`）**：xUnit v3 走 **Microsoft.Testing.Platform (MTP)**，
测试项目本身就是一个可执行程序。这不是笔误。

> ⚠️ **连带影响**：CI 的"哪些项目可以发布"分类逻辑必须先按"是不是测试项目"排除，
> 再判断 `OutputType` 是不是 `Exe`。否则测试项目会被当成可执行程序去做自包含发布（见 [05](05-GitHub工作流.md)）。

### `SampleTests.cs` 里示范了什么

这个文件同时是**测试项目骨架**和**"怎么写测试"的说明文档**（大段 XML 注释）。逐条对应：

| 示范 | 代码 | 用意 |
|---|---|---|
| 输出重定向 | `[assembly: CaptureConsole]` / `[assembly: CaptureTrace]` | v3 新能力：`Console.WriteLine` / `Debug` / `Trace` 自动进测试输出 |
| 单测 | `[Fact]` + 构造函数注入 `ITestOutputHelper` | 最基础的形态 |
| 参数化 | `[Theory]` + `[InlineData]` | 每行一组参数 |
| 强参数化 | `[TheoryDataRow<int,int,int>]` + `[MemberData]`，`WithSkip(...)`、`TestDisplayName` | 每行可带跳过/显示名/元数据 |
| 夹具 | `IClassFixture<SampleFixture>`，fixture 是独立顶层类 | 多个测试方法共享状态，类结束后框架自动释放 |
| 取消令牌 | `TestContext.Current.CancellationToken` | 超时/用户取消时可感知并传给被测代码 |
| 动态跳过 | `Assert.SkipWhen(condition, reason)` | 按运行时环境跳过（比静态 `Skip="..."` 灵活） |
| 显式测试 | `[Fact(Explicit = true)]` | 默认不跑，需在运行器里显式请求（适合耗时/特殊环境用例） |
| 网络资源 | `test/Resources/`（见 [03](03-构建体系.md) 块 6） | 避免测试直接访问网络 |

**为什么把"怎么写测试"写进注释而不是另开文档**：注释在写测试时就在眼前，
且不会与代码脱节。这也是这个模板的一贯做法（`README.txt`、`README.md` 同理）。

**`TWithSamples=false` 时**：整个示例类被换成只有一个 `HelloWorld` 的最小版本，
`SampleFixture` 也不生成 —— 保证"空壳模式"下没有任何多余的示例噪声。

## 生成项目的根 `README.md`

`zmsTemplate/README.md` 是**给生成项目的使用者的说明**（不是给模板维护者的），
用 `//#if` 条件段落按开关裁剪：CLI 章节只在 `TIsCli && TWithSamples` 时出现、
包使用指南按 `TUseDI / TUseFusionCache / TUsePolly / TUseLog` 分段，
并区分"有 DI"与"无 DI"两套代码示例。

**为什么模板里内置这么长的 README**：模板的产出物要能"自己解释自己"——
使用者拿到仓库后不需要回到模板仓库查文档。
