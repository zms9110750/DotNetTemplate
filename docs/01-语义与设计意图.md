# 01 · 语义与设计意图

## 这个项目要达成的语义

> **让「开一个新的开源 .NET 项目」从"搭半天脚手架"变成"一条命令 + 几次回车"。**

具体说，生成出来的东西必须满足三件事：

1. **能直接跑**：`dotnet build` / `dotnet test` / `dotnet run` 立刻可用，不需要再补项目、补 CI、补配置。
2. **能直接发**：推一个 tag 或点一下网页按钮，就能产出可下载的自包含包、FDD 包和 NuGet 包。
3. **能直接维护**：版本、作者、仓库地址、包选择集中在一两处，改一个地方全仓库生效。

模板不是"示例代码集合"，而是**一个项目的起点契约**：以后所有基于它的项目，目录布局、
格式化规则、CI 行为都应当一致。

## 设计目标（每条都对应后面具体的一处实现）

### 1. 开关式裁剪：要什么生成什么，不要的不留痕

请求 `--TIsLib true --TIsCli true` 就**只生成**这两个项目；没开的 GUI 项目不会以"半个空壳"的形式留在仓库里。
落点在 `template.json` 的 `modifiers`（见 [02](02-模板机制.md)），连 `MyApp.slnx` 里的项目条目也会一起裁掉。

**为什么重要**：模板如果生成一堆用不到的项目，使用者第一步就是删文件 —— 那还不如不用模板。

### 2. 两种布局，按"有没有类库"决定

- 有类库 → 类库在 `src/`，可执行示例在 `samples/`（示例是"使用者"，类库是"被使用者"）
- 无类库 → 可执行程序直接放 `src/`

**为什么**：`src/` 应该只放"要发布的东西"。有类库时 CLI/GUI 只是演示，放 `samples/` 才不会和
`pack` 的目标混淆（CI 的打包逻辑正是靠"是不是 Exe"来区分，见 [05](05-GitHub工作流.md)）。

### 3. 单一配置中枢

版本号、作者、仓库地址、程序集名、命名空间根、`InternalsVisibleTo`、测试资源、
条件包引用 —— **全部**写在 `zmsTemplate/Directory.Build.props` 里，没有一个项目文件重复定义。

**为什么**：这是"改一处、全仓库生效"的前提；也是模板裁剪后仍能保持一致的办法
（被生成的项目文件里不该出现需要同步维护的重复值）。详见 [03](03-构建体系.md)。

### 4. 约定优于配置

- 代码风格：`.editorconfig` + **编译前自动 `dotnet format`**，不靠人记得手动整理
- 目录布局：`src/` `samples/` `test/` 语义固定
- CLI 命令树：文件层级**镜像**命令树层级（`rand janken` → `Tree/Rand/Janken/`）
- 测试资源：固定放 `test/Resources/`，自动外引用到所有测试项目

**为什么**：模板的价值一半在于"减少后续决策"。约定越明确，使用者越不用问"该放哪"。

### 5. 生成即带完整 CI/CD

模板里就带一套能用的 GitHub Actions：PR 验证 + 预览包 + 三种发版方式 + 6 RID 自包含包 +
按 TFM 分组的 FDD 包 + NuGet 打包。使用者要做的主要是**在网页上点 Publish**。

**为什么**：能跑起来的 CI 通常要调半天。模板直接给出一个"已经验证过能跑"的版本，比给文档更省事。

### 6. 模板自身可维护

- 模板符号（`{{TIsLib}}` 这种，会被 `dotnet new` 替换）与编译常量（`USE_LOG` / `IS_CLI` 这种，
  由 C# 编译器处理）**严格分层**，不混用
- `Global.cs` 声明为 `copyOnly`，它的 `#if USE_*` 必须留到编译期处理
- 模板内容与打包逻辑分两层，改模板不用动 nuspec，改打包不用动模板

**为什么**：如果模板符号和 C# 预处理指令混在一起，"什么时候被谁处理"就没人说得清了。
详见 [02](02-模板机制.md) 的「两种条件语法」与 [03](03-构建体系.md) 的「Global.cs」。

## 明确的边界（不做什么）

| 不做 | 原因 |
|---|---|
| 不生成业务代码 | 模板只给骨架，示例命令（hello / rand / 猜拳）是**演示形态**，不是功能 |
| 不自动更新依赖包版本 | 包版本是"生成那一刻"的快照，后续升级由使用者的项目自己负责 |
| 不支持 .NET Framework 发布 | CI 跑在 Linux runner 上，Framework 目标无法在该环境发布；这是**有意的取舍**，README 已声明 |
| 不提供 linux-x86 (32 位) RID | .NET 6 起官方移除了 32 位 Linux 支持 |
| 不锁死具体 SDK 补丁版本 | CI 按"当年 GA 大版本"动态取（`$year - 2016.0.x`），避免每年手改 |

## 关键取舍一览（"为什么是 A 不是 B"）

| 抉择 | 选了什么 | 为什么 |
|---|---|---|
| 模板载体 | `dotnet new` + nupkg（Template 类型） | 官方机制，可 `dotnet new install`，能进私有源 |
| 裁剪方式 | 文件级 include/exclude（`modifiers`）而不是生成后删除 | 生成即干净，不留"删了一半"的痕迹 |
| 全局配置落点 | `Directory.Build.props` 而不是每个 csproj | MSBuild 自动向上查找导入，天然覆盖所有项目 |
| 编译常量来源 | MSBuild 属性 → `DefineConstants`，而不是写在 csproj | 开关是"全仓库级"的，写进单个 csproj 就失去集中性 |
| 代码风格强制手段 | 构建期 `dotnet format` 改写文件 | 见 [03](03-构建体系.md)：代价是构建变慢，收益是"不存在没格式化的提交" |
| 测试框架 | xUnit v3（MTP 模式，测试项目是 `Exe`） | 见 [04](04-项目结构与示例.md) |
| GUI 技术栈 | Photino.Blazor + Masa.Blazor | 跨三平台、无需 WPF/WinForms，见 [04](04-项目结构与示例.md) |
| 发版落点 | 草稿 Release（需手动 Publish） | 发版不可逆；人工确认产物是最后一道闸 |
