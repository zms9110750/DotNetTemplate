# 06 · 约定与已知问题

## 文件编码（最重要的一条约定）

`AGENTS.md` 里写着这条硬规则，**它是踩过坑才加的**：

> **PowerShell 写文件默认用系统 ANSI（GBK），会破坏 UTF-8 内容。**
> 含中文的文件（`.yml` / `.cs` / `.md` / `.json` / `.razor` 等）**必须**用 `edit_file` / `write_file` 工具修改，
> 禁止用 PowerShell 的 `>` / `Out-File` / `Set-Content` / here-string 重定向写入。

必须用 PowerShell 写文件时，显式指定 UTF-8 无 BOM：

```powershell
[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding($false)))
```

**这条规则在 CI 里也有体现**：两套 `ci.yml` 里凡是改写文件的地方（如替换 nuspec 版本号），
都走 `[System.IO.File]::WriteAllText` + `UTF8Encoding($false)`，而不是 `Set-Content` /
（注意：同一个脚本里生成纯 ASCII 的 `tmp.csproj` 用的是 `Out-File -Encoding utf8`，因为那份内容没有中文）。

**症状识别**（原文）：工具能 grep 到中文但 `read_file` / Node 读乱码 → 文件是 GBK，需转 UTF-8。

## `.gitignore`

实测两份 `.gitignore`（仓库根 6737 字节 / `zmsTemplate/` 6711 字节）**只差两行**：

```
# Reasonix

```

**为什么只在根**：这是模板维护者本地使用的工具目录，不该出现在"生成给别人的项目"里。
`zmsTemplate/.gitignore` 是**模板产出物的一部分**，所以保持干净。

## 已知限制（README 已声明，改动前请先读）

| 限制 | 原因 |
|---|---|
| 不能发布 .NET Framework 目标 | CI 跑在 `ubuntu-latest`，Framework 目标无法在该环境发布；需要 Windows runner 自行构建 |
| 不提供 `linux-x86` | .NET 6 起官方移除 32 位 Linux 支持 |
| 预览版 TFM 会失败 | CI 按"当年 GA 大版本"取 SDK（`$year - 2016.0.x`）；用未发布的 TFM 需手动指定 `dotnet-version` |
| 自包含发布只给最高 TFM | `Get-Highest` 的刻意选择；要发布特定 TFM 的自包含包需调整 `TargetFrameworks` 或手动构建 |

## 踩过的坑（按"症状 → 原因 → 对策"记录）

### 1. `dotnet format` 明明没跑，构建却是绿的

**症状**：SDK `11.0.100-rc.1.26425.128` 上执行 `dotnet format` 报

```
The application to execute does not exist:
'C:\Program Files\dotnet\DotnetTools/dotnet-format/dotnet-format.dll'
```

**原因**：该 SDK 去 `DOTNET_ROOT\DotnetTools` 找 `dotnet-format.dll`，而不是 `sdk\<版本>\DotnetTools`。
本机 `sdk\{8.0.127, 10.0.109, 10.0.303}` 下该文件都存在，只有 11 RC 这条路径走不通。
**关键**：这个失败**退出码是 0** —— 在 MSBuild 的 `Exec` 里属于静默失败，构建照样绿灯，但格式化根本没发生。

**对策**：用 `global.json` 把 SDK 固定到 `10.0.303` / `10.0.109`；
或升级到修复后的 11.x 正式版。**排查"格式没生效"时先确认 SDK 版本。**

### 2. 给项目加第二个 `TargetFramework` 会让格式化跑多次

**症状**：`<TargetFrameworks>net8.0;net10.0</TargetFrameworks>` 的项目，构建时会走 outer + inner 两次构建。

**现状**：模板里 `src/MyApp/MyApp.csproj` 用的是**复数** `<TargetFrameworks>`，但只有一个值
`net10.0` —— 实测这种情况下**不会**产生 outer/inner 分离，`FormatCode` 只触发 1 次。

**对策（将来加 TFM 时）**：给 `FormatCode` 加一个 TFM 门（例如
`Condition="... And ('$(TargetFramework)' == '' Or '$(TargetFramework)' == 'net10.0')"`），
或参考官方的 `DispatchToInnerBuilds` 方案。
[microsoft/agent-framework](https://github.com/microsoft/agent-framework/commit/60da0ffb4803e0db18d3d3bde8e008eb4277882c)
就在这上面踩过（"format 会跑 TFM 数量那么多遍"）。

### 3. Visual Studio 与 CLI 的 ProjectReference 行为不一致

**事实**：[dotnet/msbuild#5599](https://github.com/dotnet/msbuild/issues/5599) —— `ProjectReference` 的
`AdditionalProperties` 元数据在 **dotnet/msbuild CLI** 下会透传给被引用项目，但在 **Visual Studio 内构建时不会**
（`ResolveProjectReferences` 的 `MSBuild` 任务带 `'$(BuildingInsideVisualStudio)' != 'true'` 条件，
VS 走自己的依赖调度）。

**对本仓库的影响**：无。当前 `FormatCode` 用的是"共享辅助目标 + MSBuild 任务去重"方案，
**不依赖属性透传**，所以 VS 下同样只执行一次。
（曾经评估过用 `AdditionalProperties` 给引用项目打标记的方案，正是因为这个差异而放弃。）

### 4. 模板符号替换出来的是 `True` / `False`，不是 `true` / `false`

`{{TIsLib}}` → `True`。而 `Directory.Build.props` 里写 `'$(IsLib)' == 'true'` 能成立，
是因为 **MSBuild 字符串比较大小写不敏感**。任何"用属性值做字符串比较"的新代码都要意识到这一点。

### 5. 用本地路径安装模板时，`postActions` 的 restore 不执行

**症状**：`dotnet new install <本地路径>` 后生成项目，输出里出现
`不支持发布操作 b175a520-76f8-46f5-800c-2b55b8a0e65f`。

**原因**：该 actionId 是 NuGet 的 restore 动作，只在**以 nupkg 安装模板**时可用。

**对策**：本地验证模板时手动补一次 `dotnet restore`（不影响生成结果，只影响是否自动还原）。

### 6. `dotnet pack -p:Version=` 覆盖不了 nuspec 的版本号

两套 CI 都因此**在打包前用 PowerShell 正则替换 nuspec 里的 `<version>`**。
这是实测确认的行为，不是写法偏好。

### 7. `build/FormatOnce.proj` 不能放在模板根目录

`dotnet format` 未指定目标时，会从工作目录找**以 `proj` / `sln` 结尾**的文件作为格式化目标。
它如果放在模板根（与 `MyApp.slnx` 同级），可能被误选为格式化目标。
放在 `build/` 子目录可以规避（`dotnet format` 只扫工作目录，不递归）。

### 8. 模板内 CI 的 PR 评论标题里有 `??`

`zmsTemplate/.github/workflows/ci.yml` 的 PR 评论模板中，`📦` / `🔄` / `❌` 显示为 `??`，
是文件编码/转义留下的痕迹。**纯显示问题，不影响 CI 行为**；如要修，用 `write_file` 重写那几行。

  文档中的解释来自对 YAML 的阅读与其中注释的转述。
- **.NET Framework / 多 TFM 分支**：`Get-Highest`、`publish-fdd` 的跳过逻辑属于**阅读推断**，
  没有用真实的 netfx 项目验证过。
