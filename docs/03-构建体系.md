# 03 · 构建体系

## 全景

`zmsTemplate/Directory.Build.props` 是整个生成项目的**唯一配置中枢**。MSBuild 会从每个项目目录
向上查找并自动导入它，所以 `src/` `samples/` `test/` 下所有项目都继承同一份配置，
**没有一个项目文件重复定义版本、作者、包**。这也是模板裁剪后仍保持一致的前提。

文件分为 7 个块 + 2 个收尾项，下面逐块写清"为什么"。

---

## 块 1 · 模板符号 → MSBuild 属性

```xml
<PropertyGroup>
  <IsLib>{{TIsLib}}</IsLib>
  <IsCli>{{TIsCli}}</IsCli>
  <IsGui>{{TIsGui}}</IsGui>
  <IsTest>{{TIsTest}}</IsTest>
  <UsePolly>{{TUsePolly}}</UsePolly>
  <UseFusionCache>{{TUseFusionCache}}</UseFusionCache>
  <UseDI>{{TUseDI}}</UseDI>
  <UseLog>{{TUseLog}}</UseLog>
</PropertyGroup>
```

**为什么要有这一层**：`{{...}}` 是**模板语言**，只在生成期存在一次；替换完就变成普通字面量。
把它统一转成 MSBuild 属性后，后面所有条件判断都只依赖 `IsLib` / `UseLog` 这类**构建语言**，
不再需要模板符号。这是"模板语言 → 构建语言"的翻译层，也是模板与项目解耦的关键。

**坑**：替换结果是 `True` / `False`（首字母大写），而条件里写的是 `=='true'`。
MSBuild 的字符串比较**大小写不敏感**，所以能工作；但如果你把比较改成 C# 或脚本里的判断，就必须自己统一大小写。

## 块 2 · 编译常量

```xml
<PropertyGroup Condition="'$(UsePolly)' == 'true'">
  <DefineConstants>$(DefineConstants);USE_POLLY</DefineConstants>
</PropertyGroup>
<PropertyGroup Condition="'$(UseDI)' == 'true' Or '$(IsGui)' == 'true'">
  <DefineConstants>$(DefineConstants);USE_DI</DefineConstants>
</PropertyGroup>
```

同名规则还有 `USE_FUSIONCACHE`、`USE_LOG`。

**为什么需要这一步**：MSBuild 属性影响的是**构建**，而代码里的 `#if` 需要**编译器**认得的常量。
`DefineConstants` 是二者之间唯一的桥。没有它，`Global.cs` 与 `Program.cs` 里的条件编译就无从判断。

**为什么 GUI 强制 `USE_DI`**：`Photino.Blazor` 的入口本身就是 `appBuilder.Services`（一个 DI 容器），
GUI 代码天然依赖 DI，把 `USE_DI` 打开才能让 `Global.cs` 里的装配方法与 GUI 入口一致。

**为什么常量名是 `USE_*` 而不是 `USEPOLLY`**：与项目类型常量 `IS_CLI` / `IS_GUI` / `IS_TEST` 在命名上分开——
前者表示"启用了哪个能力"，后者表示"当前是哪种项目壳"。

## 块 3 · 包元数据 + AssemblyMetadata

```xml
<Authors>{{AuthorName}}</Authors>
<Version>0.1.0-a.0</Version>
<RepositoryUrl>https://github.com/$(Authors)/MyApp</RepositoryUrl>
<RepositoryType>git</RepositoryType>
...
<ItemGroup>
  <AssemblyMetadata Include="Authors" Value="$(Authors)" />
</ItemGroup>
```

**为什么作者要同时写进 `AssemblyMetadata`**：`AuthorName` 写在 props 里只是构建期信息，
打包后运行时读不到。`Global.cs` 的 `ConfigureHttpClient` 需要在**运行时**拼 HTTP User-Agent
（`{名字} v{版本} @ {作者}`），只能靠 `AssemblyMetadataAttribute` 反射读取。

**为什么 `RepositoryUrl` 用 `$(Authors)` 拼**：作者名即 GitHub 用户名，这样只填一个 `AuthorName`
就能同时得到作者、仓库地址、命名空间根三样东西。

**版本号 `0.1.0-a.0`**：模板给一个"明显不是正式版"的初值，提示使用者去改；
CI 发版时会用真实版本覆盖（替换 nuspec / 传入 `-p:Version`）。

## 块 4 · 程序集名与命名空间根

```xml
<RootNamespace Condition="'$(Authors)' != ''">$(Authors).$(MSBuildProjectName)</RootNamespace>
<RootNamespace Condition="'$(Authors)' == ''">$(MSBuildProjectName)</RootNamespace>
<AssemblyName>$(RootNamespace)</AssemblyName>
```

**为什么**：

- 让命名空间与程序集名一致，`Assembly.GetEntryAssembly().GetName().Name` 直接等于程序集名，
  而 `Global.cs` 的 HTTP 客户端就是以**程序集名做 key**（`AddHttpClient(name)` 与 `AddResilienceHandler(name)` 同名）——
  名字不一致会导致"注册了一个客户端、解析的是另一个"。
- `Authors` 为空时退化为纯项目名，避免生成出以 `.` 开头的命名空间。

## 块 5 · InternalsVisibleTo

```xml
<ItemGroup Condition="!$(MSBuildProjectName.EndsWith('.Test'))">
  <InternalsVisibleTo Include="$(AssemblyName).Test" />
</ItemGroup>
```

文件里的原注释写着：**「IsTest 是全局开关，不能用；用项目名是否含 .Test 判断」**。

**为什么不能用 `IsTest`**：`IsTest` 是**解决方案级**的开关（`{{TIsTest}}` 替换一次，写进 props，
所有项目看到同一个值），它回答的是"这个仓库里有没有测试项目"，**不是**"当前这个项目是不是测试项目"。
用它做条件会导致类库和测试项目都被加上 `InternalsVisibleTo`。

**为什么用项目名后缀**：命名约定是唯一的可靠信号——`$(MSBuildProjectName)` 在"当前项目"视角下取值，
`MyApp.Test` 满足、`MyApp` 与 `MyApp.Cli` 不满足。代价是**测试项目必须叫 `*.Test`**，改名会破坏这条规则。

## 块 6 · 测试资源外引用

```xml
<ItemGroup Condition="'$(IsTest)' == 'true'">
  <Content Include="$(MSBuildThisFileDirectory)test/Resources/**"
           Link="Resources/%(RecursiveDir)%(Filename)%(Extension)"
           CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
```

**为什么**：

- 资源在仓库里**只存一份**（`test/Resources/`），通过 `Link` 让所有测试项目共享，不往各项目目录复制源码树。
- `CopyToOutputDirectory` 保证运行时能按 `Resources/<文件名>` 相对路径读到。
- **核心动机是"测试不要联网"**：把远程数据下载下来放这里，测试读本地文件，这样网络不可用时测试仍能跑，
  CI 也更快更稳（`test/Resources/README.md` 有同样的说明）。

## 块 7 · 条件包引用矩阵

用 `<Choose>` 按"是否有 DI"分成两支：

| 能力 | 有 DI / GUI 分支 | 无 DI 分支 |
|---|---|---|
| FusionCache | `NeoSmart.Caching.Sqlite.AspNetCore` | `NeoSmart.Caching.Sqlite` |
| Polly + FusionCache | `Axion.Extensions.Http.Resilience.Caching.Hybrid` | `Axion.Extensions.Polly.Caching.Hybrid` + `Polly.Extensions` + `Polly.RateLimiting` |
| Polly（无缓存） | `Microsoft.Extensions.Http.Resilience` | `Polly.Extensions` + `Polly.RateLimiting` |
| Serilog（有 DI 时） | 额外 `Serilog.Extensions.Logging` / `Serilog.Extensions.Hosting` / `Soenneker.HttpClients.LoggingHandler` | — |
| 任何情况下 | `SQLitePCLRaw.lib.e_sqlite3`（开 FusionCache 时） | 同左 |

**为什么用 `<Choose>` 而不是一堆独立条件**：同一个能力在两种模式下要用**不同的包**（`.AspNetCore` vs 裸包、
`Http.Resilience` vs `Polly`），分支写法更易读，也天然保证"两个分支的包不会同时进来"。

**为什么 `SQLitePCLRaw.lib.e_sqlite3` 要显式加**：托管包不带原生 SQLite 库，缺了会在运行时找不到 native 库。

**为什么"只要开 FusionCache 就加"**：FusionCache 的 SQLite 二级缓存依赖它，与有没有 DI 无关。

## 收尾 1 · FormatCode（编译前自动格式化）

当前实现：

```xml
<Target Name="FormatCode" BeforeTargets="BeforeBuild"
        Condition="Exists('$(MSBuildThisFileDirectory).editorconfig')">
  <MSBuild Projects="$(MSBuildThisFileDirectory)build/FormatOnce.proj" Targets="FormatOnce"
           RemoveProperties="Configuration;Platform;TargetFramework;TargetFrameworks;RuntimeIdentifier;
                            BuildingSolutionFile;CurrentSolutionConfigurationContents;SolutionDir;
                            SolutionFileName;SolutionName;SolutionPath;SolutionExt;
                            BuildingInsideVisualStudio;BuildProjectReferences" />
</Target>
```

`build/FormatOnce.proj`：

```xml
<Project>
  <Target Name="FormatOnce">
    <Exec Command="dotnet format --no-restore" WorkingDirectory="$(MSBuildThisFileDirectory)..\" />
  </Target>
</Project>
```

### 为什么是现在这个形状（演进史）

**第 1 代**：直接写 `<Exec Command="dotnet format --no-restore" WorkingDirectory="模板根" />`。
`dotnet format` 不带参数会从工作目录发现 `MyApp.slnx`，于是**每个参与编译的项目都触发一次、
每次都全量格式化整个解决方案**。A→B→C 的依赖链实测跑了 **3 次**（每次 10 秒量级）。

**第 2 代**：显式传 `"$(MSBuildProjectFullPath)"`，让每个项目只格式化自己。
正确，但仍有 N 次进程启动（`dotnet format` 单次固定开销约 8–9 秒，见下）。

**第 3 代（现状）**：项目自己不再跑 `dotnet format`，而是统一调用 `build/FormatOnce.proj` 里的
`FormatOnce`。**MSBuild 对 `(项目文件, 全局属性集合, target)` 三元组做去重**，
所以整次构建里这个 target 只会真正执行一次 —— 无论 csproj 构建还是 sln 构建。

用户对这个行为的要求（原话，取自当时的对话）：

> 用户：「相当于a->b->c。只有a自己可以调出来这个命令。但这个命令同时作用于abc。也就是无论如何，启动这个程序的时间只要一份。」

### 去重原理

MSBuild 内部两级缓存，作用域是**整个构建会话**（不是单个项目）：

| 缓存 | 键 | 值 |
|---|---|---|
| `ConfigCache` | 项目文件路径 + 该次调用的全局属性集合 | 项目配置实例 |
| `ResultsCache` | 上面那个配置 + **target 名** | 该 target 的执行结果 |

三次调用若「项目路径 + 全局属性集合」完全一致，就会命中同一条 `ResultsCache` 记录：
第一个执行，后两个直接拿结果。**跨节点也如此**（实测 sln 场景 3 个项目落在不同节点，仍只执行 1 次）。

`RemoveProperties` 的作用是把从各项目继承来的全局属性摘掉，让不同来源的调用收敛到同一个配置。
**实测（本机，单 TFM 模板）**：加不加它都是 1 次 —— 因为三个项目传下去的属性集合本来就一致。
它的真实价值是**防御**：多 TFM（outer/inner 的 `TargetFramework` 不同）、`RuntimeIdentifier`、
不同来源的属性出现差异时，不摘就会退化成多次执行。

> **别把 `FormatOnce.proj` 放到模板根目录**。它放在 `build/` 子目录是刻意的：`dotnet format` 未指定目标时
> 会从工作目录（模板根）找以 `proj` / `sln` 结尾的文件，`.proj` 会被误认为是格式化目标。

### 实测数据（本机 4 逻辑核，SDK 10.0.303）

| 场景 | 真正执行 `dotnet format` | 被格式化 | 耗时 |
|---|---|---|---|
| `dotnet build A.csproj`（A→B→C） | **1 次** | A、B、C 全部 | 33.4 s |
| `dotnet build All.slnx` | **1 次** | A、B、C 全部 | 26.3 s |
| 第 1 代实现（对照） | 3 次全量 | 每次全量 | 42 s |

耗时基线（`dotnet format`，与文件数几乎无关，瓶颈是**进程启动 + MSBuild 加载 + Roslyn 工作区初始化**）：

| 项目 | `.cs` 数 | 耗时 |
|---|---|---|
| 空项目 | 0 | 8.6–8.9 s |
| 合成项目 | 1000 | 11.3–11.9 s |
| FilePathBar | 4 | 12.9 s |
| Pixiv | 56 | 8.8–9.4 s |

其他基线：`--no-restore` 省约 2 秒；`whitespace` 子命令只比全跑快约 1 秒（说明瓶颈不在编译/分析）；
`dotnet build` **默认并行**，平级项目约 1.8×、依赖链约 1.5×（4 核下的上限）。

**社区结论参考**：MSBuild 没有 `Once="true"`（[dotnet/msbuild#7437](https://github.com/dotnet/msbuild/issues/7437) 仍是未实现的需求），
官方 [Run an MSBuild target exactly once](https://learn.microsoft.com/visualstudio/msbuild/run-target-exactly-once)
只覆盖多目标场景。「共享辅助项目 + MSBuild 任务去重」是社区公认的"整个构建只跑一次"方案。

## 收尾 2 · 全局 Global.cs

```xml
<ItemGroup>
  <Compile Include="$(MSBuildThisFileDirectory)Global.cs" />
</ItemGroup>
```

**为什么用 `$(MSBuildThisFileDirectory)`**：这个路径是**相对 props 文件本身**（即模板根），
而不是相对当前项目。这样无论项目在 `src/` 还是 `samples/`（目录深度不同），都指向同一个文件。

**为什么一个 `Global.cs` 能给所有项目用**：它的内容是

1. 一组 `global using`（按 `USE_*` 条件包裹）
2. 一个 `GlobalUsing` 静态类，按 `IS_CLI` / `IS_GUI` / `IS_TEST` 与 `USE_*` 组合条件编译，
   集中放日志初始化、异常兜底、FusionCache 装配、HttpClient 装配

它**不依赖任何项目自身的状态**（不引用项目内类型），所以可以共享。
一个文件同时扮演"全局 using 源"和"基础设施装配库"两个角色。

**配套约束**：`template.json` 把 `**/Global.cs` 列为 `copyOnly`（见 [02](02-模板机制.md)），
保证它的 `#if` 留到编译期处理。

**代价**：所有项目都会编译这份文件。类库项目实际只需要它的 `global using`，
`GlobalUsing` 类靠条件编译在 lib-only 场景下不生成（注释里写明了"类壳条件 = 入口项目标记 且 方法条件之或"）。

## `.editorconfig`

```ini
[*.cs]
indent_style = space / indent_size = 4 / charset = utf-8 / end_of_line = crlf

# Allman
csharp_new_line_before_open_brace = types, methods, properties, accessors, control_blocks, anonymous_methods, lambdas_expression_body
csharp_new_line_before_else = true （catch / finally 同理）

# 流程语句强制大括号
csharp_prefer_braces = true:error

# 方法类禁止 => 表达式体
csharp_style_expression_bodied_constructors / methods / operators / deconstructors / local_functions = false:error
# 属性、索引器、访问器允许 =>（例外）
csharp_style_expression_bodied_properties / indexers / accessors = true:silent

# 空格
csharp_space_after_keywords_in_control_flow_statements = true
csharp_space_around_binary_operators = before_and_after
csharp_space_between_method_{call,declaration}_empty_parameter_list_parentheses = false

# 最后一行被注释掉：
# dotnet_diagnostic.IDE0055.severity = warning
```

**为什么禁表达式体方法**：`.editorconfig` 的注释说明这是硬性风格（`false:error`），
配合"流程语句必须有花括号"，整体趋向"一眼看得到作用域"的风格。属性和访问器被例外放行，
是为了不把 `public int X => _x;` 这类无害写法也变成错误。

**为什么最后一行 `IDE0055` 被注释掉**：文件里的原注释是「已交由编译前 dotnet format 自动处理，
不在编译时重复报警」。格式化在构建时已经跑过，再让编译器报一遍格式警告只是噪音。

## `MyApp.slnx`

- `.slnx` 是 XML 格式的解决方案文件，**可读、可被模板引擎做条件处理**（普通 `.sln` 是自定义文本格式，做不到）。
- 里面用 `<!--#if (TIsLib) -->` / `<!--#else -->` 按开关裁剪项目列表（实测生效，见 [02](02-模板机制.md)）。
- 项目按 `/src/`、`/samples/`、`/test/` 分文件夹组织（`<Folder>` 元素）。

**为什么用 slnx 而不是 sln**：条件化能力是决定性的。模板需要"生成的解决方案只列出实际生成的项目"，
纯文本 `.sln` 无法表达条件。
